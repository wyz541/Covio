## 4. 验证步骤

### V01：二维码配对和六位确认码

前置条件：三台设备未配对。第一个平台已打开配对界面。

请求模板：

```text
pairing.begin(device_display_name, capabilities)
```

预期结果：

- 发送方显示二维码。
- 二维码报价包含协议版本和设备公钥摘要。
- 接收方可以扫描二维码。
- 双端显示相同六位确认码。
- 确认码不一致时配对失败。
- 配对完成后设备记录写入成功。

实际结果字段：执行时间、设备公钥摘要、确认码是否一致、错误码、结果。

### V02：配对身份变化阻断

前置条件：两台设备已完成配对。测试设备已保存对方公钥。

请求模板：

```text
devices.list()
transfer.offer(peer_id, manifest)
```

预期结果：

- 原设备可以正常连接。
- 伪造公钥或更换设备记录后连接被阻止。
- 错误码为 `peer_identity_changed`。
- 自动恢复不能绕过身份变化。

实际结果字段：原公钥摘要、变化后公钥摘要、连接状态、错误码、结果。

### V03：接收方可见接受和拒绝

前置条件：设备已配对。发送方选择一个普通文件。

请求模板：

```text
transfer.offer({entry_count, total_bytes, manifest_hash})
```

预期结果：

- 接收方显示文件数量、总字节和发送方设备名。
- 接收方未操作前没有文件数据流。
- 接收方接受后开始传输。
- 接收方拒绝后返回 `offer_rejected`。
- 拒绝后没有最终文件。

实际结果字段：确认界面出现时间、用户选择、数据流开始时间、错误码、结果。

### V04：macOS 到 Windows 单文件

前置条件：macOS 为发送方。Windows 为目标。测试文件大小至少 `64 MiB`。

请求模板：

```text
transfer.start(task_id)
```

预期结果：

- 接收方收到 `FileBegin`、分块和 `FileEnd`。
- 发送方使用稳定文件句柄。
- 接收窗口不超过 `8 MiB`。
- 文件最终 BLAKE3 一致。
- 最终文件只在校验通过后出现。

实际结果字段：文件大小、分块数、耗时、峰值内存、BLAKE3 对比、结果。

### V05：Windows 到 macOS 目录

前置条件：测试目录包含普通文件和空目录。测试目录不包含符号链接。

请求模板：

```text
transfer.offer(manifest)
```

预期结果：

- 清单保留空目录。
- 目录树按清单顺序创建。
- 所有普通文件校验通过。
- 目标目录没有 `.part` 文件。
- 目标目录没有暂存目录残留。

实际结果字段：条目数、空目录数、文件摘要、残留清单、结果。

### V06：直连失败后 relay 回退

前置条件：两台设备已配对。测试网络阻断设备间 UDP 直连。Relay 可达。

请求模板：

```text
transfer.start(task_id)
```

预期结果：

- 连接状态显示直连尝试。
- 直连失败后选择 relay。
- Relay 路径不传输明文文件内容。
- 任务最终完成。
- 传输路径记录为 relay。

实际结果字段：直连尝试结果、relay 连接时间、传输路径、错误码、结果。

### V07：`10 GiB` 大文件流式传输

前置条件：目标卷有足够空间。测试文件至少 `10 GiB`。

请求模板：

```text
transfer.start(task_id)
```

预期结果：

- 传输不使用无界内存。
- 发送窗口保持在 `8 MiB` 左右。
- 进度按持久确认字节增长。
- 传输中断后可以从检查点恢复。
- 最终 BLAKE3 一致。

实际结果字段：文件大小、分块数、峰值内存、持久检查点、恢复次数、结果。

### V08：冲突 `keep_both`

前置条件：目标目录已有同名文件。接收方选择 `keep_both`。

请求模板：

```text
transfer.accept(task_id, {conflict_policy: "keep_both"})
```

预期结果：

- 旧文件内容不变。
- 新文件使用唯一名称。
- 两个文件都存在。
- 新文件校验通过。

实际结果字段：旧文件摘要、新文件摘要、新文件路径、结果。

### V09：冲突 `replace` 原子提交

前置条件：目标目录已有同名文件。接收方选择 `replace`。

请求模板：

```text
transfer.accept(task_id, {conflict_policy: "replace"})
```

预期结果：

- 新内容先写入暂存文件。
- 暂存文件通过分块和文件校验。
- 替换前执行同步。
- 替换失败时旧文件保持可见。
- 替换成功后只保留新文件。

实际结果字段：旧文件摘要、暂存摘要、替换结果、错误码、结果。

### V10：分块损坏和重试

前置条件：测试构建提供受控损坏分块入口。目标文件未提交。

请求模板：

```text
test.inject_chunk_corruption(entry_id, chunk_index)
```

预期结果：

- 接收方检测 `chunk_hash_mismatch`。
- 只重试受影响分块。
- 连续三次失败后任务失败。
- 失败任务没有最终文件。

实际结果字段：注入位置、重试次数、错误码、最终文件状态、结果。

### V11：路径穿越和符号链接拒绝

前置条件：测试目录包含 `../` 路径和符号链接。

请求模板：

```text
transfer.offer(manifest)
```

预期结果：

- `../` 路径返回 `path_invalid`。
- 符号链接返回 `symlink_refused`。
- 符号链接目标内容没有被读取。
- 接收根之外没有新文件。

实际结果字段：拒绝项、错误码、接收根清单、结果。

### V12：网络断开后检查点续传

前置条件：传输已完成至少 `32 MiB`。执行人可断开网络。

请求模板：

```text
network.disconnect()
transfer.resume(task_id)
```

预期结果：

- 任务进入 `waiting_network`。
- 已确认字节保持持久。
- 网络恢复后从检查点继续。
- 不从头重传已确认分块。
- 最终文件校验通过。

实际结果字段：断开前确认字节、恢复后确认字节、重传字节、结果。

### V13：磁盘空间不足暂停和恢复

前置条件：目标卷剩余空间小于测试文件大小。

请求模板：

```text
transfer.start(task_id)
```

预期结果：

- 任务进入暂停状态。
- 错误码为 `insufficient_space`。
- 暂存文件保留。
- 空间恢复后可以继续。
- 最终文件校验通过。

实际结果字段：可用空间、暂停错误码、恢复时间、结果。

### V14：应用崩溃后任务恢复

前置条件：传输已完成至少 `32 MiB`。执行人可强制结束应用。

请求模板：

```text
app.terminate()
app.launch()
transfer.resume(task_id)
```

预期结果：

- 重启后任务记录存在。
- 检查点不超过已同步字节。
- 暂存文件存在。
- 恢复后不提交未校验内容。
- 最终文件校验通过。

实际结果字段：崩溃前确认字节、重启后检查点、恢复结果、结果。

### V15：用户取消和暂存清理

前置条件：传输正在进行。发送方和接收方都可以取消。

请求模板：

```text
transfer.cancel(task_id, initiator)
```

预期结果：

- 任务状态变为 `cancelled_by_sender` 或 `cancelled_by_receiver`。
- 不再发送新分块。
- 已完成文件保留。
- 暂存文件按 `24 h` 策略保留。
- 用户选择立即删除时可以删除暂存文件。
- 不出现未完成最终文件。

实际结果字段：取消发起方、取消状态、暂存文件状态、结果。

### V16：离线队列和源文件变化

前置条件：设备已配对。接收方离线。发送方加入任务队列。

请求模板：

```text
queue.enqueue(task_id)
queue.resume_on_online()
```

预期结果：

- 离线队列只保存元数据。
- 接收方上线后先显示接收请求。
- 源文件变化时返回 `source_changed`。
- 用户确认后重新生成清单。
- 未确认时没有文件内容发送。

实际结果字段：队列记录、源文件变化、错误码、结果。
