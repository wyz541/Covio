# 调研方法与技术分析

> 本文件记录 Paseo 源码分析、Rust 候选方案、反证和研究缺口。

## 1. 调研方法

调研日期为 `2026-11-10`。
Paseo 使用固定 commit `2e1747a145cd11c2f6ba7ef9fd8745a1a5b4455b`。
检查范围为 `packages/relay`、`packages/server`、`packages/app` 和 connectivity 文档。
Rust 方案使用 RFC 原文、固定版本源码仓库和 crates 元数据。
Paseo 代码只用于提取设计原则。没有复制产品代码。
没有执行 Paseo 端到端测试。
没有执行 Covio 传输原型。

## 3. 领域模型

```text
用户界面
  -> 传输 API
    -> 配对与身份
    -> 任务状态机
      -> 清单与路径策略
      -> 调度与重试
      -> 传输适配器
        -> 直连 QUIC
        -> relay 回退
      -> 分块校验
      -> 暂存写入
      -> 持久检查点
      -> 原子提交
```

核心不变量如下。

1. 文件内容只能进入已接受的任务。
2. 最终文件只能来自已验证的暂存文件。
3. 检查点不能超过已同步的字节范围。
4. 路径解析不能离开接收根目录。
5. 设备身份变化必须阻止自动恢复。
6. Relay 不能获得明文文件内容。
7. 恢复不能依赖内存中的旧 socket。
8. 取消不能删除用户已有的最终文件。

## 4. 约束模型

### 4.1 网络约束

局域网可能阻断组播。
NAT 可能阻断入站连接。
移动网络可能频繁切换地址。
Relay 可能延迟、断开或限流。
QUIC 处理包重传和拥塞控制。
应用处理会话中断、用户暂停和持久恢复。

### 4.2 移动端约束

iOS 可以挂起进程。
系统挂起后，socket 可能保留“已连接”表象。
只有收到有效入站帧才能证明连接存活。
后台任务时间有限。
后台通知不能保证启动传输。
首版不承诺后台持续接收。

### 4.3 文件系统约束

Windows 路径不区分大小写。
macOS 默认路径通常不区分大小写。
POSIX 和 Windows 的权限模型不同。
符号链接可能造成越界读取或写入。
同卷重命名通常比跨卷复制更可靠。
原子替换需要平台文件系统适配。

### 4.4 安全约束

二维码可能被拍照、替换或重放。
局域网攻击者可以伪造发现记录。
Relay 运营者可以记录连接元数据。
接收文件名可能包含路径穿越序列。
接收清单可能包含超大字段或无限重复项。
设备私钥不能发送给对端。
文件内容和配对密钥不能进入普通日志。

## 5. 控制路径

### 5.1 配对路径

1. 发送方生成短期配对报价。
2. 发送方显示二维码。
3. 接收方扫描二维码。
4. 双方建立临时安全通道。
5. 双方显示同一配对确认码。
6. 发送方确认接收方身份。
7. 接收方确认发送方身份。
8. 双方保存对方公钥。
9. 双方结束短期配对会话。

### 5.2 传输路径

1. 发送方枚举文件项。
2. 发送方生成清单摘要。
3. 发送方发送摘要和可见确认请求。
4. 接收方选择冲突策略。
5. 接收方接受或拒绝任务。
6. 发送方打开控制流和文件数据流。
7. 接收方写入暂存文件。
8. 接收方持久记录已同步字节。
9. 接收方验证分块和文件。
10. 接收方原子提交最终文件。
11. 双方记录完成状态。

### 5.3 恢复路径

1. 应用重启或回到前台。
2. 核心读取任务和检查点。
3. 核心重新验证连接。
4. 核心重新验证对端身份。
5. 核心比较清单摘要和检查点。
6. 发送方从持久确认字节继续。
7. 接收方截断未确认尾部。
8. 接收方继续正常传输。

## 6. 信任边界

| 边界 | 信任对象 | 不信任对象 | 控制 |
| --- | --- | --- | --- |
| 配对 | 二维码短期报价 | 扫描者身份 | 一次性密钥和双端确认 |
| 设备身份 | 已固定公钥 | 新公钥和变化公钥 | 身份变化阻断 |
| 网络 | QUIC 加密信道 | 局域网和公网路径 | TLS 1.3 和应用签名 |
| Relay | 密文转发能力 | Relay 运营者 | 端到端加密和元数据最小化 |
| 文件系统 | 应用沙箱目录 | 接收路径内容 | 路径校验和不跟随链接 |
| UI | 用户明确选择 | 自动默认接受 | 可见确认和冲突提示 |

| 能力 | 来源 | 用途 | 限制 |
| --- | --- | --- | --- |
| QUIC 多流 | RFC 9000 | 控制流与文件流隔离 | 需要 UDP 可达或 relay |
| TLS 1.3 | RFC 9001 | 身份验证、机密性和完整性 | 证书和公钥策略需要自建 |
| 丢包恢复 | RFC 9002 | 网络丢包处理 | 不保存应用级检查点 |
| quinn | `0.11.12` | 纯 Rust QUIC 传输 | 不提供 P2P 发现和 relay |
| iroh | `1.4.1` | 公钥寻址、打洞、relay 回退、QUIC | 版本较新，移动端需验证 |
| iroh-relay | `1.4.1` | 自建 relay 和访问控制 | Relay 可观察元数据 |
| iroh-ffi | `1.2.0` | Swift 和 Kotlin 绑定 | 高层文件协议不在稳定范围 |
| mDNS | RFC 6762 和 RFC 6763 | 局域网服务发现 | 无身份保证，组播可能被阻断 |

| BLAKE3 | crate `1.8.7` | 文件和分块校验 | FIPS 合规性未评估 |
| SHA-256 | crate `0.11.1` | 外部兼容校验 | 平台性能未实测 |
| SQLite | `rusqlite 0.41.1` | 任务和检查点持久化 | 需要事务和迁移设计 |
| 原子写入 | `tempfile 3.27.0`、`atomic-write-file 0.3.1` | 暂存和提交 | 跨卷和平台行为未实测 |

## 8. Paseo 目标产品分析

### 8.1 固定版本事实

Paseo 源码包含 `packages/relay`、`packages/server` 和 `packages/app`。
Paseo 使用 WebSocket 作为客户端与 daemon 的应用协议。
Paseo 的 relay 是不可信转发通道。
Paseo 的 protected 模式使用 `Noise_NK_25519_ChaChaPoly_SHA256`。
Paseo 的 Noise prologue 为 `paseo-relay-e2ee/1`。
Paseo 每次新建 daemon 安全信道时生成新的临时密钥。
Paseo 使用计数器防止重放。
Paseo 在记录认证失败后关闭信道。
Paseo 的客户端可以固定 daemon 公钥。
Paseo 的二维码报价包含 `serverId`、daemon 公钥和 relay 地址。
Paseo 在添加新主机或改变主机身份时要求用户确认。
Paseo 的配对流程支持可选的 host 认证凭据。
Paseo 的客户端在前台重新执行连接验证。
Paseo 的普通心跳间隔为 `10 s`。
Paseo 连续两次心跳失败后拆除连接。
Paseo 前台验证使用两个 `5 s` 窗口。
Paseo 前台验证失败后立即重连。
Paseo 普通重连从 `1500 ms` 开始，最大 `30000 ms`。
Paseo 的可恢复订阅在重连后重新建立。
Paseo 在断线时清除旧等待者和旧发送队列。
Paseo 的文件帧使用 `FileBegin`、`FileChunk` 和 `FileEnd`。
Paseo 文件传输使用 `256 KiB` 分块。
Paseo 每个文件读取使用稳定的文件句柄。
Paseo 每个分块等待对应物理发送完成。
Paseo 文件传输按来源 socket 隔离。
Paseo 连接有 `8 MiB` 发送高水位。
Paseo 已连接主机文档记录 `100 MiB` 消息上限。

以上观察见 [evidence.md](evidence.md) 中的 `E-01` 至 `E-05`。

### 8.2 可复用原则

| 原则 | Paseo 证据 | Covio 采用方式 |
| --- | --- | --- |
| 二维码携带公钥而非匿名地址 | `E-02` | 二维码携带设备公钥指纹和短期报价 |
| 用户确认新增或变化身份 | `E-02` | 双端显示配对确认码 |
| Relay 不可信 | `E-03` | 只发送端到端密文 |
| 身份固定而非地址固定 | `E-03` | 任务绑定设备公钥 |
| 前台主动验活 | `E-04` | iOS 回到前台后立即探测 |
| 指数退避 | `E-04` | 重连使用有上限的退避和抖动 |
| 订阅恢复而非请求盲重放 | `E-04` | 文件任务从持久检查点恢复 |
| 有界分块 | `E-05` | 首版使用 `1 MiB` 分块 |
| 有界发送窗口 | `E-05` | 首版使用 `8 MiB` 窗口 |
| 传输来源隔离 | `E-05` | 每个任务独立控制上下文 |

### 8.3 不能直接复用的部分

Paseo 的主要产品目标是 daemon 控制和会话流。
Paseo 的文件帧没有定义目录清单、冲突策略和原子提交。
Paseo 的 WebSocket relay 方案不提供 QUIC 流优先级。
Paseo 的二维码报价不包含双向文件接收确认。
Paseo 的设备身份主要验证 daemon 一侧。
Covio 需要双向设备身份和文件任务语义。
因此 Covio 只复用安全原则和恢复原则。

## 9. 候选方案分析

### 9.1 方案 A：quinn 自建完整传输

组成如下。

- `quinn 0.11.12` 提供 QUIC。
- `rustls` 提供 TLS 1.3。
- Covio 自建地址交换、relay 和打洞。
- Covio 自建直连和 relay 选择。

优点如下。

- 协议控制最完整。
- 可以使用自有 relay 和自有证书策略。
- 依赖层较少。
- quinn 已在 macOS 和 Windows 的 README 中列为测试平台。

风险如下。

- NAT 穿透工作量大。
- Relay 协议和部署需要独立团队。
- 地址发现和隐私策略需要自建。
- iOS 网络切换和后台恢复仍需自测。
- 没有现成 P2P 连接迁移经验。

### 9.2 方案 B：iroh 加 Covio 文件协议

组成如下。

- `iroh 1.4.1` 提供端点、公钥寻址、QUIC、打洞和 relay 回退。
- `iroh-relay 1.4.1` 提供可自建 relay。
- Covio 定义清单、分块、确认、校验和落盘。
- `iroh-ffi` 只用于验证能力，不作为最终 FFI 合同。

优点如下。

- 直接解决公网设备寻址和 NAT 穿透。
- 直连优先，relay 自动回退。
- QUIC 提供并发流和应用层数据报。
- Relay 可以自建并配置访问控制。
- 与 Paseo 的“公钥身份加不可信 relay”原则一致。

风险如下。

- iroh 仍处于快速演进阶段。
- 公共 relay 的隐私和依赖需要评估。
- iOS 编译、二进制体积和耗电尚未实测。
- 高层 blob 协议不在 iroh FFI 的稳定范围。
- 需要固定完整依赖树和协议版本。

### 9.3 方案 C：mDNS 加原始 TCP 或 QUIC

优点如下。

- 局域网零配置发现简单。
- 适合 AirDrop 类邻近体验。
- 不依赖公网 relay。

风险如下。

- mDNS 不提供认证。
- mDNS 广播会暴露服务元数据。
- 企业网络和访客网络可能阻断组播。
- 跨网络完全不可用。
- 需要另行解决身份和加密。

### 9.4 方案 D：HTTP 或 WebSocket 加 relay

优点如下。

- 实现成熟。
- 代理和防火墙兼容性较好。
- Paseo 已有相似 relay 经验。

风险如下。

- 大文件多流隔离需要额外设计。
- WebSocket 消息边界和队头阻塞需要处理。
- NAT 直连仍需独立方案。
- 移动端后台恢复仍需应用协议支持。

### 9.5 方案 E：iroh-blobs 直接复用

优点如下。

- BLAKE3 内容寻址。
- 已验证流和范围请求。
- 适合内容分发和去重。

风险如下。

- 需要额外的文件清单和接收确认层。
- Windows 和 iOS 的文件语义仍需 Covio 定义。
- 高层 blob 协议未进入 iroh FFI 稳定范围。
- 会增加首版协议和存储复杂度。

### 9.6 候选方案对比

| 方案 | 成本 | 风险 | 成熟度 | 可维护性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| quinn 自建 | 高 | 高 | 高 | 中 | 保留为回退 |
| iroh 加自有协议 | 中 | 中高 | 中高 | 高 | 推荐 |
| mDNS 加原始 QUIC | 中 | 高 | 中 | 中 | 只做发现补充 |
| HTTP 或 WebSocket relay | 中 | 中 | 高 | 中 | 不作为首版主路径 |
| iroh-blobs 直接复用 | 中高 | 中高 | 中 | 中高 | 后续评估 |

## 10. 反证和限制

### 10.1 反证

iroh 的下载量低于 quinn。成熟度不能只按下载量判断。
quinn 的平台列表没有明确列出 iOS。iOS 需要单独验证。
mdns-sd 官方 README 标注 beta。不能把 mDNS 作为唯一发现路径。
Paseo 的 relay 使用 WebSocket 和 Noise。Covio 使用 QUIC 后不能直接复用该线协议。
Paseo 的文件传输没有目录清单和原子提交语义。
BLAKE3 的性能优势需要真实设备基准支持。
SHA-256 的合规优势不能替代文件冲突和恢复设计。

### 10.2 研究限制

- 没有执行 Covio 原型编译。
- 没有执行 iroh iOS 构建。
- 没有执行 quinn iOS 构建。
- 没有执行真实 NAT 穿透测试。
- 没有测量公共 relay 延迟和可用性。
- 没有测量 BLAKE3 和 SHA-256 吞吐。
- 没有验证 Windows 原子替换行为。
- 没有验证 macOS 大小写和 Unicode 行为。
- 没有验证 iOS 后台暂停时序。
- 没有验证设备密钥的硬件后备能力。

## 11. 已知缺口

| 缺口 | 影响 | 后续验证 |
