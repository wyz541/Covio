# 根因、结论与限制

> 本文件给出推荐决策、决策依据、不采用方案和未决项。

## 1. 结论摘要

[推论] Covio 首版应使用 `iroh 1.4.1` 作为传输底座。
[推论] Covio 应自建文件协议，不直接复用 iroh 高层 blob 协议。
[推论] 首版应使用固定 `1 MiB` 分块和 `8 MiB` 发送窗口。
[推论] 首版应使用 BLAKE3 作为分块和文件主校验。
[推论] 首版应把 SHA-256 作为兼容字段，不放入关键路径。
[事实] Paseo 使用二维码分发 daemon 公钥。Paseo 在用户确认后固定身份。
[事实] Paseo 把 relay 视为不可信通道。
[事实] Paseo 在前台重新验证连接，并从连接状态恢复订阅。
[推论] Covio 应保留“身份固定、relay 不可信、前台复核、检查点恢复”四项原则。
[推论] mDNS 只能提供候选地址。mDNS 不能提供设备身份或接收授权。
[推论] iOS 后台不能保证持续传输。首版应暂停并持久化，前台再恢复。
[推论] 接收端必须先写暂存文件。校验通过后才能原子提交最终文件。

关键证据见 `E-01` 至 `E-13`。

## 2. 主要根因或决策因素

### 2.1 主要因素

#### 因素一：首版需要跨网络连接能力

[事实] QUIC 提供多流、流控和连接迁移。
[事实] quinn 提供纯 Rust QUIC。quinn 不提供 P2P 发现和 relay。
[事实] iroh 提供公钥寻址、打洞、relay 回退和 QUIC。
[事实] iroh-relay 支持自建和访问控制。
[推论] 直接使用 quinn 会增加 NAT 穿透和 relay 建设成本。
[推论] iroh 更符合第一版范围。
证据：`E-06`、`E-07`、`E-08`、`E-09`。

#### 因素二：身份与 relay 信任必须分离

[事实] Paseo 的二维码报价包含 daemon 公钥。
[事实] Paseo 的客户端会固定 daemon 公钥。
[事实] Paseo 的 relay 只转发密文。
[事实] Paseo 的 protected 模式使用新的临时密钥和计数器。
[推论] Covio 的设备身份不能绑定 IP 地址、mDNS 名称或 relay 地址。
[推论] Covio 应固定设备公钥。公钥变化必须要求重新确认。
[推论] Covio 可以允许 relay 不可信。Covio 不能允许明文经过 relay。
证据：`E-02`、`E-03`。

#### 因素三：移动端生命周期不能被网络层隐藏

[事实] Paseo 在 `10 s` 周期执行连接心跳。
[事实] Paseo 连续两次失败后拆除连接。
[事实] Paseo 回到前台后使用两个 `5 s` 窗口重新验活。
[事实] Paseo 前台验活失败后立即重连。
[事实] Paseo 后台只保持正常重连策略。Paseo 不保证系统继续执行。
[推论] Covio 必须把“连接有效”和“应用可运行”分开建模。
[推论] Covio 必须持久记录检查点。Covio 不能依赖旧 socket。
[推论] iOS 后台状态应显示为暂停。界面不能显示为失败。
证据：`E-04`。

#### 因素四：文件完整性必须端到端验证

[事实] QUIC 提供传输层完整性和加密。
[事实] QUIC 的丢包恢复不保存应用级检查点。
[事实] Paseo 使用稳定文件句柄和 `256 KiB` 有界分块。
[事实] Paseo 的连接发送有 `8 MiB` 高水位。
[推论] Covio 需要应用级分块校验和文件校验。
[推论] Covio 需要固定发送窗口，避免内存无限增长。
[推论] Covio 需要持久检查点，避免每次恢复从头重传。
证据：`E-05`、`E-06`、`E-07`。

### 2.2 次要因素

[事实] mDNS 提供局域网 DNS 服务发现。
[事实] mDNS 依赖合作参与者。mDNS 不提供强身份认证。
[事实] mdns-sd 官方 README 标注 beta。
[推论] mDNS 适合补充邻近设备体验。mDNS 不适合作为首版唯一发现机制。
证据：`E-10`。

[事实] BLAKE3 和 SHA-256 都是 256 位散列函数。
[事实] BLAKE3 适合并行树形散列。SHA-256 有广泛标准和兼容性。
[事实] 本次没有执行三平台吞吐基准。
[推论] 首版使用 BLAKE3 作为主校验。
[推论] 外部互操作需要时再增加 SHA-256。
证据：`E-11`。

## 3. 决策表

| 决策 | 选择 | 原因 | 备选路径 |
| --- | --- | --- | --- |
| 首版传输底座 | iroh `1.4.1` | 公钥寻址、打洞、relay 回退和 QUIC | quinn 自建 relay |
| 文件协议 | Covio 自有协议 | 需要目录、确认、冲突和续传语义 | iroh-blobs |
| 局域网发现 | mDNS 可选补充 | 邻近体验好，但不能提供信任 | 仅二维码 |
| 设备身份 | 公钥固定加双端确认 | 防止地址替换和身份替换 | 只信任 relay |
| Relay 信任 | 不可信 | Paseo 原则和端到端加密 | 信任 relay |
| 主散列 | BLAKE3 | 分块校验和并行潜力 | SHA-256 主校验 |
| 兼容散列 | SHA-256 可选 | 外部清单和合规需求 | 仅 BLAKE3 |
| 分块大小 | `1 MiB` | 便于窗口控制、校验和恢复 | `256 KiB` |
| 发送窗口 | `8 MiB` | 与 Paseo 的高水位原则一致 | 无上限流水线 |
| 接收检查点 | SQLite 加文件同步 | 可跨重启恢复 | 只依赖内存 |
| 最终提交 | 同卷暂存后原子重命名 | 防止半成品成为最终文件 | 直接写目标路径 |
| 冲突默认值 | `keep_both` | 避免无意覆盖 | `replace` |
| 符号链接 | 首版拒绝 | 跨平台和越界风险高 | 保留链接 |
| iOS 后台 | 暂停并持久化 | 系统不保证后台执行 | 声称后台持续接收 |
| 首版平台 | macOS、Windows、iOS | 用户给定范围 | 同时支持 Android |
| 发布方式 | GitHub Release 内测 | 当前产品策略 | 正式商店发布 |

## 4. 逻辑证据链

### 4.1 观察一：Paseo 把身份与地址分离

观察：二维码包含 daemon 公钥和 relay 地址。
推论：地址可以变化。设备身份不能随地址变化。
置信度：高。
证据：`E-02`。

### 4.2 观察二：Paseo 的 relay 不持有明文

观察：Paseo 在 relay 上运行 `Noise_NK_25519_ChaChaPoly_SHA256`。
推论：Relay 可以转发密文。Relay 不能读取文件内容。
置信度：高。
证据：`E-03`。

### 4.3 观察三：Paseo 的前台验活不依赖旧 socket

观察：Paseo 使用新的前台探测周期。
推论：Covio 回到前台后不能假设旧连接仍然有效。
置信度：高。
证据：`E-04`。

### 4.4 观察四：Paseo 的文件传输是有界流

观察：Paseo 使用 `256 KiB` 分块和 `8 MiB` 高水位。
推论：Covio 需要固定窗口和背压。
置信度：高。
证据：`E-05`。

### 4.5 观察五：QUIC 解决传输，不解决持久恢复

观察：RFC 9002 定义包级丢失检测和探测超时。
推论：应用必须记录文件级检查点。
置信度：高。
证据：`E-06`、`E-07`。

### 4.6 观察六：iroh 覆盖首版 P2P 需求

观察：iroh 提供公钥寻址、打洞、relay 回退和 QUIC。
推论：iroh 降低首版网络工程成本。
置信度：中高。
证据：`E-08`、`E-09`。

### 4.7 观察七：mDNS 不能作为身份根

观察：RFC 6762 把名称冲突解决描述为合作参与者的算法。
推论：mDNS 记录不能证明设备身份。
置信度：高。
证据：`E-10`。

### 4.8 观察八：完整性需要双层设计

观察：传输层校验不能替代应用级文件校验。
推论：Covio 需要分块校验和最终文件校验。
置信度：高。
证据：`E-05`、`E-11`。

## 5. 不采用方案

### 5.1 纯 quinn 首版

不采用原因如下。

- 需要自行实现地址发现。
- 需要自行实现 NAT 穿透。
- 需要自行部署 relay。
- 需要自行处理连接迁移和回退策略。

风险如下。

- 首版网络工程量过高。
- 跨网络验证周期不可控。
- iOS 网络切换测试范围扩大。

保留条件如下。

- iroh 无法通过 iOS 真机验收。
- iroh 的 relay 隐私不满足内部测试要求。
- Covio 必须使用完全自有 relay 协议。

### 5.2 直接复制 Paseo 的 WebSocket 和 Noise 协议

不采用原因如下。

- Paseo 协议服务于 daemon 控制。
- Paseo 协议不提供文件目录清单。
- Paseo 协议没有冲突和原子提交语义。
- 复制产品代码不满足本次研究边界。

可复用内容仅为安全原则和恢复原则。

### 5.3 只使用 mDNS 发现

不采用原因如下。

- mDNS 不提供身份。
- mDNS 在部分网络被阻断。
- mDNS 不能跨互联网工作。
- mDNS 广播会暴露服务元数据。

mDNS 只作为候选地址提示。

### 5.4 首版直接复用 iroh-blobs

不采用原因如下。

- 首版需要自己的接收确认和冲突语义。
- 需要支持目录和空目录。
- 需要定义 Windows 和 iOS 的提交语义。
- iroh-ffi 未把高层 blob 协议列入稳定范围。

后续可以用 iroh-blobs 评估去重和范围传输。

### 5.5 使用无界流水线

不采用原因如下。

- 内存会随网络和磁盘速度差增长。
- 应用后台时可能丢失大量未持久数据。
- 取消和暂停响应会变慢。

首版使用固定窗口和背压。

### 5.6 直接写最终文件

不采用原因如下。

- 网络中断会留下可见半成品。
- 校验失败会破坏目标文件。
- 应用崩溃后无法判断文件是否完整。

首版使用同卷暂存文件和原子提交。

### 5.7 声称 iOS 后台持续传输

不采用原因如下。

- iOS 可以随时挂起应用。
- 普通网络 socket 不保证后台继续运行。
- 系统通知不保证启动传输。

首版使用后台暂停和前台恢复。

## 6. 系统限制

- iroh 的公共 relay 仍可观察连接元数据。
- QUIC 需要 UDP。受限网络可能需要 TCP relay 或代理。
- iOS 后台没有持续 QUIC 保证。
- Windows 大小写和保留名称与 POSIX 不同。
- macOS 默认文件系统可能进行 Unicode 规范化。
- 同卷原子重命名有文件系统前提。
- 接收端必须保留暂存空间。
- 大目录会增加清单和冲突检查时间。
- 符号链接和 ACL 不在首版完整支持范围。
- 任何加密方案都不能修复用户主动确认错误设备的问题。

## 7. 产品限制

- 首版只支持 macOS、Windows 和 iOS。
- Android 只保留协议和 FFI 入口。
- 首版不支持实时目录同步。
- 首版不支持匿名投递。
- 首版不支持无接收方确认的自动接收。
- 首版不保证后台接收。
- 首版不承诺跨卷原子提交。
- 首版不保证保留完整权限元数据。
- 首版只通过 GitHub Release 做内部测试。
