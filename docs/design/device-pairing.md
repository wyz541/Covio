# Covio 设备身份与二维码配对

- 状态：accepted
- 日期：2026-11-10
- 决策：[ADR-0035](../adr/adr-0035-cross-platform-product-scope.md)
- 研究：[Rust 文件传输](../research/rust-file-transfer/README.md)
- 依赖：[Covio 凭据仓库](credential-vault.md)

## 1. 结论

Covio 使用长期 Ed25519 密钥标识设备。
Covio 使用 X25519 临时密钥建立一次性配对共享秘密。
二维码只分发公开身份、临时公钥和短期报价。
双端从已签名 transcript 派生六位确认码。
六位确认码不能单独完成配对。

## 2. 设备身份

设备首次启动时生成 32 字节 Ed25519 种子。
种子保存到 `credentials/device-identity/credential-vault.json`。
Rust 凭据仓库用平台安全存储保护根密钥。
设备身份 vault 与 Agent token vault 分开。
平台安全存储不直接保存长期私钥。

公开身份包含以下字段。

| 字段 | 含义 |
| --- | --- |
| `device_id` | Ed25519 公钥的完整 SHA-256 指纹 |
| `display_name` | 用户可见设备名 |
| `public_key` | Ed25519 公钥的十六进制值 |

`device_id` 格式为 `sha256:<64 hex>`。
配对协议在读取身份时重算指纹。
指纹不一致时拒绝身份。

## 3. 二维码报价

二维码 payload 前缀为 `covio-pair/1/`。
前缀后是 JSON 报价。
报价字段如下。

| 字段 | 用途 |
| --- | --- |
| `protocol_version` | 配对协议版本 |
| `offer_id` | 一次配对报价的随机标识 |
| `sender_device_id` | 发起端公钥指纹 |
| `sender_display_name` | 发起端设备名 |
| `sender_public_key` | 发起端 Ed25519 公钥 |
| `sender_ephemeral_public_key` | 发起端 X25519 临时公钥 |
| `expires_at_ms` | 报价过期时间 |
| `capabilities` | 发起端协议能力 |
| `signature` | 发起端 Ed25519 签名 |

报价默认有效期为 `120000` ms。
能力列表排序并去重。
报价签名覆盖全部报价字段。
接收端先验证签名，再接受报价。

## 4. 配对流程

1. 发起端生成 X25519 临时密钥。
2. 发起端签名报价。
3. 发起端显示二维码。
4. 接收端扫描二维码。
5. 接收端验证报价签名和有效期。
6. 接收端生成 X25519 临时密钥。
7. 接收端签名响应。
8. 接收端显示六位确认码。
9. 发起端验证响应签名。
10. 发起端显示六位确认码。
11. 两个用户核对六位确认码。
12. 双端分别提交正确确认码。
13. 双端保存可信设备记录。
14. 双端销毁临时共享秘密。

接收端使用以下响应字段。

| 字段 | 用途 |
| --- | --- |
| `protocol_version` | 配对协议版本 |
| `offer_id` | 对应二维码报价 |
| `responder_device_id` | 接收端公钥指纹 |
| `responder_display_name` | 接收端设备名 |
| `responder_public_key` | 接收端 Ed25519 公钥 |
| `responder_ephemeral_public_key` | 接收端 X25519 临时公钥 |
| `signature` | 接收端 Ed25519 签名 |

响应签名为 `covio-pair-response/1/` payload。
响应签名绑定报价签名。
发起端拒绝其他报价的响应。

## 5. 六位确认码

双端使用 X25519 共享秘密。
双端使用以下字段构造 transcript。

- 报价签名。
- 响应签名。
- `offer_id`。
- 双端 Ed25519 公钥。
- 双端 X25519 临时公钥。

transcript 使用 SHA-256 摘要。
HKDF-SHA256 从共享秘密派生 8 字节。
前 8 字节取模 `1000000`。
结果格式化为六位十进制数字。
确认码比较使用常量时间比较。

确认码只用于用户核对。
确认码不进入二维码。
确认码不进入持久记录。
确认码不进入日志。
确认码错误时当前会话结束。
`PairingInitiatorAwaitingConfirmation` 只能由已签名响应创建。
`finish` 只存在于该类型。
因此，单独提交六位码不能建立信任。

## 6. 持久记录

可信设备记录保存在 `pairing/registry.json`。
记录包含以下字段。

- `device_id`。
- `display_name`。
- `public_key`。
- `paired_at_ms`。
- `last_seen_ms`。

注册表还保存以下状态。

- 已消费的 `offer_id`。
- 已撤销的 `device_id`。

注册表使用版本化 JSON。
注册表使用原子文件写入。
注册表重启后恢复。
可信设备上限为 `256`。
已消费报价上限为 `4096`。

## 7. 重放与撤销

成功完成配对时，双端消费当前 `offer_id`。
重复使用同一 `offer_id` 返回 `ReplayDetected`。
过期报价返回 `OfferExpired`。
撤销设备删除可信记录。
撤销状态写入注册表。
撤销后重启仍保持不受信任。
同一设备重新完成二维码配对后可以恢复信任。

## 8. 错误码

| Code | 含义 | 可重试 |
| --- | --- | --- |
| 2001 | 输入无效 | 否 |
| 2002 | 设备身份不存在 | 否 |
| 2003 | 协议或记录版本不支持 | 否 |
| 2004 | 配对报价过期 | 否 |
| 2005 | 报价签名无效 | 否 |
| 2006 | 响应签名无效 | 否 |
| 2007 | 响应与报价不匹配 | 否 |
| 2008 | 设备尝试与自身配对 | 否 |
| 2009 | 六位确认码不匹配 | 否 |
| 2010 | 配对报价已使用 | 否 |
| 2011 | 可信设备注册表已满 | 否 |
| 2012 | 注册表存储失败 | 是 |
| 2013 | 注册表或身份记录损坏 | 否 |
| 2014 | 平台凭据后端不可用 | 是 |
| 2015 | 内部错误 | 否 |

错误消息不包含私钥、共享秘密、二维码明文或六位确认码。

## 9. 测试

测试覆盖以下场景。

- 身份创建和重启恢复。
- 二维码报价序列化和签名验证。
- 双端确认码一致。
- 双端可信记录持久化。
- 报价过期。
- 自配对拒绝。
- 响应与报价不匹配。
- 报价和响应篡改。
- 错误确认码。
- 单独六位码不能建立信任。
- 已消费报价重放。
- 设备撤销和重启恢复。

## 10. 未决事项

- 网络传输层由 #738 接入。
- 二维码显示和扫描界面由平台 host 接入。
- 可信设备列表 UI 由平台 host 接入。
- Secure Enclave、TPM 和 Android Keystore 的硬件签名能力需要后续评审。
- 多进程同时写入注册表需要单独加锁或迁移到 SQLite。
